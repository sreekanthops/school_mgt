# School Management Suite (multi-school)

React (Vite) frontend + Python (FastAPI) backend with a grounded AI assistant.
One platform, many schools: every school's data is fully isolated.

## Run it

Requires Python 3.13 (3.9 is end-of-life) and Node 20+.

```bash
# 1. Backend  (http://127.0.0.1:8000, API docs at /docs)
cd backend
/opt/homebrew/opt/python@3.13/bin/python3.13 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env
.venv/bin/python -m app.seed --reset   # demo data; generates passwords into backend/.env
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000

# 2. Frontend (http://127.0.0.1:5173)
cd frontend
npm install
npm run dev
```

Tests: `cd backend && .venv/bin/pip install -r requirements-dev.txt && .venv/bin/python -m pytest -q tests`

## IDs and logins

Every person's ID is also their login name: **school id + year + role letter + number**.

| Who | Format | Example |
|---|---|---|
| Student | `<school><year>s<class 2 digits><roll 3 digits>` | `12026s09011` = school 1, 2026, class 9, roll 011 (LKG = `90`, UKG = `91`, class 10 = `10`) |
| Teacher / staff | `<school><year>t<3 digits>` | `12026t007` |
| Principal | `<school><year>p<3 digits>` | `12026p001` |
| School owner | `<school><year>o<3 digits>` | `12026o001` |

IDs are generated by the server, never edited, and unique across the platform because the school id
is part of them, so two schools can never share a login name. Adding a student or a school in the
app creates the ID and login together and shows the one-time temporary password once. Staff get their
ID when added; create their login in Users & Access by picking the staff profile (login = staff ID).

## Roles and permissions

- **superadmin** has no school and sees no student-level pages. Uses the Platform Console below.
- **admin** (school owner) holds every permission and manages users.
- **staff** get only the permissions an admin ticks: `students.view`, `students.manage`, `marks.edit`,
  `fees.view`, `fees.manage`, `staff.manage`, `subjects.manage`, `content.manage`, `school.manage`,
  `photos.approve`, `attendance.manage`, `announcements.manage`, `users.manage` (admin-only to grant). Nobody can grant a permission they lack.
- **student** sees only their own record. Their new profile photo waits for approval before it shows.

Edit controls (add / edit / delete) appear only where the user holds the matching permission.

## Platform Console (superadmin)

- **Console home:** totals for schools, branches, students, staff and fee collection; charts for students and
  staff per school, schools onboarded over 12 months, fee collection, students per class and plan mix; a
  "needs attention" list (expired or expiring subscriptions, schools at 90% of a limit, disabled schools); recent activity.
- **School cards:** each school has buttons for Details, Edit, Branches, Owner password, Disable/Enable and Delete.
- **School detail page:** profile (board, type, city, contact, website, private notes), plan and subscription,
  student/staff limit usage, last activity, class-wise academics and fee charts, branches (add, edit, make main,
  disable, delete), owner and staff logins (reset password, disable) and a per-school activity trail.
- **Plan limits:** a school cannot add students or staff beyond the limits the superadmin sets (HTTP 403 with a clear message).
- **Audit trail:** every superadmin action is recorded (who, when, what; never a password) and kept even after a school is deleted.
- **Subscription reminders and lock:** owners and staff see a banner at 30, 14 and 7 days before the end date
  (reminders 1, 2 and 3 of 3; the last one is red). After the end date the school becomes **read-only**: owners
  and staff can still sign in and view everything, but every add, edit, delete, payment and marks entry is refused
  by the server (HTTP 403) and the buttons are faded in the UI. Messaging, the assistant and changing your own
  password stay open. **Students are never affected** and see no banner. Renewing (set a new end date) unlocks
  at once; a school with no end date never locks. The superadmin can still manage an expired school.
- **Data note:** the superadmin sees only counts and aggregates (no individual marks or student profiles).
- API: `GET /api/platform/overview`, `GET/PUT /api/schools/{id}`, `/api/schools/{id}/branches`, `/api/audit`; all superadmin-only.

## Anonymous Idea Board

- Everyone in a school (owner, staff, students) can post a short note (3 to 300 characters) about school life. Notes
  look like handwritten sticky notes (the bundled Caveat font, no external requests).
- **Anonymous by design:** a note stores only a keyed hash of the writer, never a user id, and no API returns who
  wrote or voted. Writers can delete their own notes; owners/staff with `content.manage` can remove any note.
- **Language filter (server-side):** profanity, sexual wording, slurs, threats and abuse in English plus common
  Hindi/Telugu words in English letters are refused, including disguised forms ("sh1t", "f u c k", "fuuuck").
  Phone numbers, e-mail addresses and links are refused too. The editor warns as you type; the refusal never
  repeats the offending word. A word list cannot catch everything, which is why moderators can remove notes.
- **Voting:** only students vote, one vote per student per note (voting again changes it, tapping again removes
  it), not on their own note. Each note shows % agree, % disagree, vote count and the share of students who voted.
  Sort by newest, most agreed or most debated. Posting is limited to 5 notes per 15 minutes per person.

## Forgot password

1. **Set up** (My Account → Password recovery questions): the app picks 3 random questions from a bank of 12; the
   user answers them. Answers are normalised (case/punctuation ignored) and stored only as bcrypt hashes.
2. **Forgot?** (sign-in page → "Forgot password?"): enter the Login ID, get the same 3 questions again, answer all
   three and choose a new password. Five wrong attempts lock recovery for that ID for 15 minutes. Unknown IDs and IDs
   that never set recovery up get the same questions-shaped response and the same generic failure.
3. **Still stuck?** The school admin / IT department (anyone with `users.manage`; the superadmin for an owner) issues
   a **temporary password** from Users & Access → key icon. It is shared in person (the user contacts the office),
   works for sign-in only, and the user is forced to choose their own password before anything else.

## Announcements

The owner (or anyone with `announcements.manage`) posts notices to **everyone, staff only, students only, or one class**.
People only ever receive the notices meant for them (a student sees "everyone", "students" and their own class).
Posts can be pinned. The sidebar shows an unread count; opening the page marks them read. Text is stored and shown
as plain text, never HTML. The assistant answers "any announcements?".

## Exports (CSV and PDF)

Students, marks summary, fee register (filter by class/status), attendance report, **report card** (one student, PDF)
and **fee receipt** (one payment, PDF). Needs `students.view` (lists) or `fees.view`/`fees.manage` (fees); a student can
download only their own report card and receipts. CSV text that starts with `= + - @` is prefixed with `'` so a
spreadsheet cannot run it as a formula. Downloads are reads, so they keep working when a subscription has expired.

## Bulk actions

- **Import students** (Students → Import): CSV or Excel `.xlsx`, up to 300 rows / 2 MB. Download the template first.
  Class can be written `5`, `Class 5`, `5th`, `LKG`; dates as `2014-06-21` or `21/06/2014`. The file is **checked first
  (dry run) and nothing is saved until every row is valid**; duplicates (same name, birth date and class) are flagged.
  Each student gets an ID/login and a one-time password that must be changed at first sign-in; the list is shown once
  and can be downloaded. The plan's student limit is enforced.
- **New academic year** (Students → New year, needs `school.manage` + `students.manage`): moves every student up one
  class, lets you tick students to **hold back**, and optionally removes Class 10 leavers. IDs and logins do not change;
  last year's marks and fees stay and are selectable by year. It can only run once per year (a second click is refused).
  The school's current year is stored per school (`schools.academic_year`; `CURRENT_ACADEMIC_YEAR` is the default).
- **Set fee for a class** (Fees page).

## Staff logins

Adding a staff member now also creates their login (login = staff ID, one-time password, forced change at first
sign-in) with standard teacher permissions (`students.view`, `marks.edit`, `attendance.manage`; the principal also gets
`fees.view` and `announcements.manage`). You can never give a new login more than you hold yourself, and you can
untick "create login" with `?create_login=false`. Deleting a staff member deletes their login.

## Attendance

Teachers (`attendance.manage`) mark a class and date as Present / Late / Absent (Late counts as attended); saving again
edits the day. No future dates, and nothing older than 90 days. Reports by class and date range with a daily trend,
a per-student attendance tab (with month-by-month chart), and **alerts**: under 75% over the last 30 days (once at least
5 days are recorded) or absent 3 school days in a row. Alerts show on the Dashboard and the assistant answers
"who has low attendance?" / "what is my attendance?" (students only for themselves).

## Billing (Platform Console)

Superadmin → Schools → **Billing & renewals** (and a Billing tab on each school): invoice list with status
(Pending / Overdue / Paid / Cancelled), collected / awaiting / overdue totals, a monthly chart and a **renewal tracker**
(nearest end date first, with a button to raise an invoice). An invoice defaults to the plan price (Free 0, Standard
24,000, Premium 60,000 per year) plus 18% tax, starting the day after the current subscription ends; all of that can be
overridden. **Mark paid** records mode and reference and moves the school's subscription end date to the end of the
invoice period, so the expired/reminder state clears by itself. Invoices have a PDF. Every step goes in the audit
trail, and invoices are kept even if the school is deleted. The owner has a read-only **Billing** page for their own
school's invoices; staff and students cannot see billing.

## Smart import (existing school data)

**Smart Import** (Admin menu) loads a school's existing records from one file: Excel (`.xlsx`, every sheet), CSV, JSON
(flat, nested or keyed by ID) or a Word (`.docx`) table. It handles students, staff, subjects, marks, fees, fee payments,
events and goals, in any order within one file.

1. **Upload.** Each sheet is read, titles above the table are skipped, and the sheet is classified and its columns
   mapped by rules (headings such as "Pupil Name", "Adm No", "Unit Test 1", "Father Name", "6A" are understood).
2. **Review.** You can correct what each sheet is, and which column is which. Nothing has been written yet.
3. **Check.** A dry run (the same code as the real run, then rolled back) reports per sheet: new / already there /
   updated / skipped, every problem with its row number, differences from what the system holds, and plan-limit blockers.
4. **Confirm.** Only possible with zero problems; all-or-nothing in one transaction.
5. **Undo.** Every confirmed import is recorded; undo within 7 days removes what it created (and restores values it updated,
   if nobody has edited them since).

No duplicates or overlap: students match on the old ID, or on name + date of birth + class; staff on old ID, or name +
phone, or name + email; marks on student + subject + exam + year; fees on student + year; events on title + date.
Importing the same file twice changes nothing. Marks and fees find students by old/admission ID, or by name (+ class and
section if two share a name; ambiguous names are reported, never guessed). A fee sheet's "paid" column records only the
difference from what the system already holds. Marks out of a different maximum are scaled; blank/absent marks are skipped.
If the file and the system disagree, the system's value is kept unless you choose "use the file's value".

Safety: passwords are never imported (new students and staff get a one-time password and must change it); permissions are
capped at the importer's own; each sheet needs the matching permission (`students.manage`, `staff.manage`, `marks.edit`,
`fees.manage`, `subjects.manage`, `content.manage`); the plan's student and staff limits are enforced; uploads are limited
to 5 MB / 5,000 rows per sheet, macro-enabled and old binary Office files and files with XML entity tricks are refused;
the uploaded file is kept only until confirm/cancel, or 24 hours at most; the whole feature is read-only while a
subscription has expired.

**Optional AI help.** If `LLM_BASE_URL` (https only), `LLM_API_KEY` and `LLM_MODEL` are set, sheets the rules could not map are
sent to the model for a suggestion. **Only the sheet name and column headings are sent, never any row of data**, and the
answer is validated (only known fields and real headings are accepted) and shown for you to correct. Without it, everything
still works by rules.

## Messaging rules

Owners and staff can message anyone in their school. Students can message staff and the owner, never
other students. Nothing crosses schools. Clearing a chat hides it for you only; the other person keeps
their copy. Message text is stored as plain text and rendered escaped.

## Chatbot design

Answers come from database queries only (no model-generated SQL), so it cannot invent data or
leak beyond what the logged-in user may see (a student asking about another student or about
fees gets a refusal). Optionally set `LLM_BASE_URL` (https only), `LLM_API_KEY`, `LLM_MODEL` in
`backend/.env` to have an OpenAI-compatible model rephrase the facts; if unset or failing it
falls back to the grounded answer.

## Security notes

- Passwords hashed with bcrypt; JWT sessions (60 min); 5 failed logins lock a username for 15 min
- Multi-tenant: every query is filtered by `school_id`; cross-school access returns 404
- RBAC checked on every request server-side; the UI only hides buttons as a convenience
- Inputs validated server-side (Pydantic); ORM only, no raw SQL
- Photos are served only through authenticated endpoints, validated by magic bytes, max 3 MB
- Servers bind to 127.0.0.1; CORS restricted; generic 500 errors, details only in server logs
- Secrets only in `.env` (git-ignored). Front-end token lives in sessionStorage
